# 可维护性五因素自评报告（§8.4.1）

本报告基于当前版本文字 MUD 项目源码（`src/`）进行自评，评分采用 1-5 分制（5 分最高）。

## 1) 可理解性（3/5）

### 评价依据

- 优点：模块边界基本清晰（`room/player/enemy/command/game_engine`），类名和职责较直观。
- 不足：部分业务流程集中在 `GameEngine.main_game_loop` 与 `AttackCommand.execute`，阅读时需要跨多段逻辑才能理解状态变化。

### 本轮改进

- 将命令解析与战斗状态判定从主循环中抽取为独立方法，降低单方法复杂度：
  - `_parse_command`
  - `_try_enter_combat`
  - `_is_command_blocked_in_combat`

## 2) 可测试性（2/5）

### 评价依据

- 迭代前无自动化单元测试，回归风险高。
- 逻辑含随机数（攻击伤害）与输出分支，若无测试桩难以稳定验证。

### 改进方案（已实施）

- 新增 `tests/`，补充回归单测 5 个，覆盖移动、拾取限制、战斗掉落、状态输出与战斗命令限制。
- 使用 `pytest` + `monkeypatch` 固定随机行为，保证测试可重复。
- 通过 `conftest.py` 统一配置 `src` 导入路径，降低测试样板代码。

## 3) 可修改性（3/5）

### 评价依据

- 优点：命令模式（`Command` 抽象类 + 具体命令）便于新增命令。
- 不足：部分命令内部包含业务细节耦合（例如战斗与掉落流程紧耦合在 `AttackCommand` 中），修改战斗规则时影响面偏大。

### 改进建议（后续迭代）

- 将“战斗结算/掉落结算”进一步拆分为独立服务函数（如 `combat_service.py`），命令层只负责调度。
- 为关键业务规则建立表驱动测试（不同敌人属性、不同玩家状态）。

## 4) 可移植性（3/5）

### 评价依据

- 项目基于标准 Python 与 pytest，跨平台运行成本低。
- 但目前未明确声明 Python 版本区间与本地运行入口规范，可能导致环境差异问题。

### 改进方案（已实施）

- 在 README 中补充本地环境搭建步骤（克隆、创建虚拟环境、安装依赖、运行测试、启动游戏）。
- 在 CI 中统一 Python 版本并执行自动测试，减少“本地可运行但 CI 失败”的概率。

## 5) 可重用性（2/5）

### 评价依据

- 当前核心逻辑与命令行 I/O（`print/input`）耦合，复用于 GUI/Web 接口时需要重写交互层。
- 缺少统一的领域服务层接口，不利于二次开发。

### 改进方案（本轮+后续）

- 本轮先完成局部重构，将一部分流程控制从主循环抽离，为后续分层打基础。
- 后续建议：
  - 引入“纯逻辑层 + 交互适配层”结构；
  - 领域对象方法返回结构化结果（而非直接打印）；
  - CLI 仅负责渲染输出。

---

## 本次迭代结论

- 低于 3 分的因素：**可测试性（2/5）**、**可重用性（2/5）**。
- 已针对可测试性完成实质改进（新增并接入 CI 的回归测试）。
- 可重用性已给出分层重构方案，建议在下一次迭代中作为重点任务落实。
